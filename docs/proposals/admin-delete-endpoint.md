## 0. 背景と目的

管理画面には試合（`events`）の削除手段が存在しない。このため、

- 動作確認用のテストデータを登録すると、**画面からは二度と消せない**
- 誤登録した試合が実運用の一覧に恒久的に残る

という問題がある。本機能はこれを解消するものである。

**2026-07-31、KMT様の判断により実装が決定した。**

---

## 1. 【必須】実装前の確認 —— 外部キー制約

**この確認を行う前に実装へ着手してはならない。**

`cheer_logs` は `events` を参照している。この外部キーの削除時挙動によって、
DELETE実装の危険度が正反対になる。

```sql
SELECT conname, confdeltype
FROM pg_constraint
WHERE conrelid = 'cheer_logs'::regclass AND contype = 'f';
```

`confdeltype` の値の意味：

| 値 | 意味 | 評価 |
|---|---|---|
| `r` | RESTRICT | 安全。参照があれば削除は失敗する |
| `a` | NO ACTION（無指定時の既定） | 安全。同上 |
| `c` | **CASCADE** | **危険。試合を消すと応援ログが全件、無言で削除される** |

**`c`（CASCADE）だった場合、本設計のまま実装してはならない。**
その事実を報告し、KMT様の判断を仰ぐこと。
（本設計はアプリ側で件数チェックを行うため二重の防御にはなるが、
CASCADEが設定されている状態そのものが、将来の別経路からの事故要因となる）

この確認は**staging環境（`cheerstick_staging`）で行えばよい。**
本番スキーマと完全一致していることは2026-07-30に確認済みである。

## 2. 設計

### 2.1 エンドポイント

```
DELETE /api/v1/admin/events/:id
```

既存の `/api/v1/admin/*` 配下に置く。nginxのIP制限
（`allow 49.156.217.121; deny all;`）がそのまま適用される。

### 2.2 削除を許可する条件（**サーバー側で強制すること**）

以下の**両方**を満たす場合のみ物理削除を行う。

1. 対象試合の `status` が `live` **ではない**こと
2. 対象試合を参照する `cheer_logs` が **0件**であること

テストデータおよび誤登録は、いずれもこの条件に該当する。
**実際に応援が記録された試合は、構造的に削除できない。**

### 2.3 レスポンス

| 状況 | ステータス | 内容 |
|---|---|---|
| 削除成功 | 200 または 204 | — |
| 対象が存在しない | 404 | `EVENT_NOT_FOUND` |
| `status` が `live` | 409 | 進行中の試合は削除できない旨 |
| `cheer_logs` が1件以上 | 409 | **件数を含めて返す**。「応援データが N件あるため削除できません。終了させる場合は `finished` にしてください」 |

### 2.4 実装上の注意

- **FK制約に削除の可否を委ねないこと。** 必ずコード側で `cheer_logs` の件数を
  `SELECT COUNT(*)` で確認し、明示的に判定する。
  FK違反の例外を握って409に変換する実装にはしない
  （既知の課題5「不正UUID形式で500＋生のPostgreSQLエラーが返る」と
  同種の問題を再生産するため）
- `:id` のUUID形式バリデーションを**必ず入れること。**
  既知の課題5がこのエンドポイントにも波及するのを防ぐ
- 削除前後の状態を `console.log` 等で記録すること
  （認証がない以上、誰が消したかは追えないが、何が消えたかは残す）

### 2.5 UI（管理画面）

**単純な `confirm()` は使用しない。**

削除ダイアログで**試合名を手入力させ、一致した場合のみ削除ボタンを有効化**する
方式とする。当日の慌ただしい場面での誤クリックが、そのまま実害になる操作である
ことを踏まえた措置。

409で拒否された場合は、返却された理由（応援データ件数など）を画面に表示する。

## 3. 実装時期と順序（2026-07-31 決定）

**本機能を、2026-07-31の案B本番反映に含めないこと。**

理由：
- 同日のデプロイには既に未検証の変更が5種類（11コミット分の反映、本番誤接続
  ガードの初投入、nginx新規serverブロック、DNSレコード追加、証明書取得）
  同時に入る。ここにDELETEを加えると、障害時の切り分けが不可能になる
- DELETEは、認証のないAPIに追加する**最も破壊的なエンドポイント**である

**決定した順序：**

1. 案Bの本番反映を完了させる（`docs/proposals/production-deploy-plan.md`）
   - 当日の動作確認は、テストデータではなく**本番用の初回試合データの登録**を
     もって行う（KMT様判断。これによりテストデータ削除の必要が生じない）
2. staging環境（ポート3001、`cheerstick_staging`）でDELETE機能を実装・検証
   - 本文書「1. 実装前の必須確認」を最初に実施する
3. 単独のデプロイとして本番へ反映する

手順1が完了していれば、手順3は同じ経路を2度目に通るだけとなり、
リスクは大きく下がる。

---

## 4. 本機能では対応しない事項

- 論理削除（`deleted_at` 等）の導入 —— 物理削除で足りるため見送り
- 削除の監査ログ —— 管理APIの認証が未実装（既知の課題2）であり、
  操作者を特定できない以上、監査ログとしての意味を持たない。
  認証実装とセットで再検討する
- `cheer_logs` そのものの削除機能 —— 本機能の対象外

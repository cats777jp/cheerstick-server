## 0. 背景（方針転換の経緯）

旧方針（物理DELETE）は、実装前の必須確認として `cheer_logs`→`events` の
外部キー制約（`confdeltype`）を確認する前提だった。

2026-07-31、staging環境での確認により `confdeltype = 'n'`（**SET NULL**）と
判明した。これは旧設計が想定していた3択（RESTRICT / NO ACTION / CASCADE）
のいずれでもない。

`events` の行を物理削除すると、参照する `cheer_logs.event_id` が
**自動的にNULLへ書き換わる。** 行自体は消えないため件数は減らず、
「何も起きていないように見えて、実は応援ログがどの試合のものか
分からなくなる」という、CASCADEより発見しづらい形でデータが壊れる。

この事実を踏まえ、KMT様の判断により**物理削除は行わず、非表示化
（論理削除）方式に変更する。**

---

## 1. 概要

管理画面の「削除」操作は、`events` 行を消さず、**非表示フラグを立てる**。

- ユーザー側（Vanstone様アプリ）・管理画面の**両方**から見えなくなる
- データは物理的に残るため、`confdeltype`の値に関わらず安全
- 誤操作時は、Claude Code経由の直接DB操作でフラグを戻せば復元できる
- **本当の物理削除**は、管理画面には持たせず、EC2への直接アクセス
  （Claude Code経由）でのみ行う運用とする

---

## 2. スキーマ変更

```sql
ALTER TABLE events ADD COLUMN hidden_at TIMESTAMPTZ NULL;
```

- `NULL` = 表示中、`NOT NULL`（タイムスタンプが入っている） = 非表示
- 単純な真偽値（`is_hidden BOOLEAN`）ではなく`hidden_at`とするのは、
  「いつ非表示にしたか」を残すため（設計方針として、操作者は特定できないが
  何が・いつ変わったかは残す、という旧設計2.4の考え方を踏襲）

---

## 3. エンドポイント

```
DELETE /api/v1/admin/events/:id
```

HTTPメソッドは`DELETE`のまま維持する（管理画面のUIとしては「削除」操作
であることに変わりはなく、実装が非表示化であることは内部の話のため）。

### 3.1 許可条件

**`status`が`live`の試合は非表示化を禁止する。**（KMT様判断：誤操作防止を優先）

| 状況 | ステータス | 内容 |
|---|---|---|
| 非表示化成功 | 200 または 204 | — |
| 対象が存在しない | 404 | `EVENT_NOT_FOUND` |
| `status`が`live` | 409 | `CANNOT_HIDE_LIVE_EVENT`（「進行中の試合は削除できません。停止してから操作してください」） |

旧設計にあった「`cheer_logs`が0件であること」という条件は**撤廃する。**
物理削除を行わないため、応援ログの有無は非表示化の可否に無関係になった。

### 3.2 実装内容

```sql
UPDATE events SET hidden_at = now() WHERE id = :id;
```

- `:id`のUUID形式バリデーションは旧設計どおり維持する（既知の課題5対策）
- 変更前後の状態をログに残す（旧設計2.4を踏襲）

---

## 4. 表示制御（両方の経路で必須）

### 4.1 管理画面（一覧取得API）

既定で `hidden_at IS NULL` の行のみを返す。非表示にした試合を管理画面上で
再表示・復元するUIは**設けない**（復元はClaude Code経由の直接DB操作のみ、6章参照）。

### 4.2 ユーザー側（Vanstone様アプリが参照する経路）

**要確認：** `events`を参照している全てのエンドポイント（管理系以外、
一般公開系のAPI）を洗い出し、`hidden_at IS NULL`のフィルタを漏れなく
適用する必要がある。旧設計では物理削除だったため考慮不要だったが、
非表示化方式では**この横展開が実装の要**になる。

対象候補（要棚卸し。以下は一例であり、Claude Codeによる洗い出しが必要）：
- 一般APIのうち`events`を参照する箇所全般

---

## 5. UI（管理画面）

- ボタン表記は**「削除」のまま**でよい（内部実装が非表示化であることは
  利用者に意識させる必要がない）
- 確認は**簡易な確認ダイアログ**とする（旧設計の「試合名の手入力必須」方式は
  廃止）。ただし文言は「本当に削除しますか？」等、削除であることが
  明確に伝わる内容にすること（実際にはデータを消さない、という実装都合を
  UI文言に反映する必要はない）
- 409（`live`のため拒否）の場合、その旨を画面に表示する

---

## 6. 復元・本当の削除の運用

いずれも管理画面・APIには持たせない。**Claude Code経由の直接DB操作のみ**で行う。

### 6.1 誤って非表示化した場合の復元

```sql
UPDATE events SET hidden_at = NULL WHERE id = '<対象ID>';
```

### 6.2 本当にデータを物理削除する場合

EC2への直接アクセスで実施する。実施前に、`cheer_logs`が当該`event_id`を
参照しているかを確認すること。`confdeltype='n'`のため、確認なしに
`DELETE FROM events`を実行すると、参照する`cheer_logs`が無言でNULL化される。

```sql
-- 削除前に必ず確認
SELECT COUNT(*) FROM cheer_logs WHERE event_id = '<対象ID>';
```

件数が0でない場合、`cheer_logs`側の扱い（それも合わせて削除するか、
`event_id`がNULLのまま残すことを許容するか）をKMT様と相談のうえ判断する。
この運用は`docs/runbook.md`に追記すること。

## 7. 実装順序

旧設計3章の方針を踏襲する。

1. staging環境（`cheerstick_staging`、ポート3001）で実装・検証
   - マイグレーション（`hidden_at`列追加）
   - エンドポイント変更（非表示化ロジック、`live`ガード）
   - 管理画面一覧APIのフィルタ
   - **ユーザー側エンドポイントの洗い出しとフィルタ適用**（4.2）
   - 管理画面UIの確認ダイアログ簡略化
2. 単独のデプロイとして本番へ反映する（7/31の案B反映とは分離）

## 8. 本機能では対応しない事項

- 管理画面からの復元・再表示UI（6.1の運用で代替）
- 管理画面からの物理削除（6.2の運用で代替。EC2直接アクセスのみ）
- 削除の監査ログ（旧設計4章と同様。認証実装とセットで再検討）

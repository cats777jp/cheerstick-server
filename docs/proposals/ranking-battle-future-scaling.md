# 対抗戦順位発表画面：大規模イベント時の将来対応（記録のみ）

作成日：2026-10-07。**未実装・今回は対応しない。** `docs/spec.md` 9.14（`ranking-battle.html`）は現状規模（約1,000人）を前提に作った。
8,000人・20,000人規模で使う場合に必要になる事項を、後日の判断材料として記録する。

## 1. 課題：順位確定1回の所要時間

出典：2026-10-07の調査（`createRankingSnapshot`、`src/db/cheerstickQueries.js`）。

【事実】
- 順位確定は、ユーザー別・選手別の2本の集計クエリを1トランザクション内で順に実行する（`computeUserRanking`／`computeTargetRanking`）。
- どちらも`WHERE cl.event_id = $1`に一致する**全行**を読んで`SUM(intensity)`を取る（上位20件だけを返すが、読む行数は減らない）。
- 使われるインデックスは`idx_cheer_logs_event_id`・`idx_cheer_logs_event_target`で、いずれも`intensity`を含まないため行ごとにヒープを読みに行く。
- 順位確定は`events.status`を変更せず、`count`の受信・`cheer_logs`への書き込みの経路にも触れない（試合は止まらない）。

【推測】（実測ではない。`large-event-scaling.md`の「約4.4万行で23〜25ms」＝1行あたり約0.55µsからの外挿）

| その試合の`cheer_logs`行数 | 1本あたり | 確定全体（2本） |
|---|---|---|
| 数万行（現状規模） | 数十ms | 0.1秒未満 |
| 720万行 | 約4秒 | 約8秒 |
| 2,300万行 | 約12秒 | 約25秒 |

## 2. 規模が大きくなったときの影響（対抗戦画面）

- 対抗戦では「両チーム順位確定」でA・Bの確定を同時に呼ぶ。2試合分の集計が同時にDBへ載り、所要時間・DB負荷はさらに増える（同じEC2に同居のDBのCPU・I/Oを`count`のINSERTと取り合う）。
- 確定中は接続プール（`max: 20`）の1本を占有する。確定ボタンの連打で占有が積み上がる。
- ユーザー別と選手別は別々のSELECT（READ COMMITTED）のため、確定中に届いた`count`ぶんの食い違いが、所要時間と同じ長さに広がる。対抗戦ではA・Bの確定時刻のずれも加わる。
- 画面側は確定済みスナップショットを読むだけなので、画面の表示自体は規模に影響されない（ポーリングは1リクエスト/3秒、スコアAPIと同じレート制限・キャッシュ）。

## 3. 対策案（優先順は未決）

出典：`large-event-8000-investigation.md` S4・G章、`large-event-scaling.md` C-2。

1. **確定の前に試合を`paused`にする運用**：`count`の記録が止まり、確定中のずれが無くなる。コード変更不要。ただし試合中の確定は不可。
2. **集計用インデックスの追加**：`(event_id, user_id)`・`(event_id, target_id)`に`intensity`を含める（Index-Only Scan化）。行数に比例するコスト自体は残る。インデックス追加は書き込みを重くする（現在9本）。
3. **走行合計の別テーブル化**（`large-event-8000-investigation.md` S4）：`count`受信時にユーザー別・選手別の合計を加算し、確定時は上位20件を直接取る。確定は速くなるが、`count`の書き込みが増える。
4. **確定を非同期化**：ボタンは受付だけ返し、裏で集計。管理画面は完了をポーリング。

## 4. 実測が必要なこと

- 本番相当のデータ量（720万行・2,300万行）での`EXPLAIN (ANALYZE, BUFFERS)`。本番DBへの接続は岩村様の判断で、または一時EC2（`multi-process-config-draft.md` 7章）で。
- 確定中の`count`のINSERT遅延（`pg_stat_activity`・応答時間）。
- 上位EC2・DB同居／RDSの選択（`handoff-2026-10-06.md`）に依存する。

## 5. 判断の目安

- 現状規模（約1,000人）：対応不要。
- 8,000人規模の契約が決まった時点で、上記「実測が必要なこと」から着手する。

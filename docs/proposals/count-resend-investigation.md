# アプリの再送仕様が`cheer_logs`の記録に与える影響の調査

作成日：2026-10-06
対象コミット：`feature/reference-data`（調査開始時点のHEAD）
性質：**読み取りのみ。** コード・設定は変更していない。本番EC2・WebARENA・本番DBへの接続も行っていない。
位置づけ：検討中資料。実装済みの仕様ではない（`docs/spec.md`とは別）。

背景（依頼文）：ネイティブアプリは、通信が確立できなかったデータを保持し、確立した時点でサーバーへ送る。
再接続のあと、保持していた`count`がまとめて届く可能性がある。

## 凡例

- **【事実】**：コード・docsを読んで確認できたこと（`ファイル:行`を付記）
- **【推測】**：事実からの導出・外挿
- **【未確認】**：コードからは分からず、Vanstone様（ネイティブ側）への確認や実機確認が必要なこと

## 0. 先に結論

| # | 結論 | 区分 |
|---|---|---|
| 1 | **`cheer_logs.cheered_at`は常にサーバーのINSERT時刻**（`DEFAULT NOW()`）。クライアントの`count`に時刻・連番のフィールドは**無く**、サーバーも読まない。したがって「遅れて届いた`count`」は、**届いた時刻に発生したものとして記録される** | 事実 |
| 2 | **WebView（`index.html`）自身は再送もバッファもしない。** WebSocketが開いていない間の`send()`は黙って捨てる。さらに再接続すると応援中画面が隠れ、**STARTを押し直すまで`onCheerStickData`は何も処理しない**。したがって、ネイティブが保持データを再接続後に`onCheerStickData`へ流し込んでも、**START前なら全部捨てられる** | 事実（コード）。ネイティブ側の再送がどの層の話かは【未確認】 |
| 3 | 試合終了後に届いた`count`は、**live試合が無ければDBへ記録されない**（破棄）。ただし`cached`モードでは終了から最大2秒間は旧`event_id`で記録されうる。**次の試合がliveなら、その`event_id`に記録される**（発生時刻ではなく受信時刻で振り分けられる） | 事実 |
| 4 | **サーバーに重複排除の仕組みは無い。** `count`に冪等キーが無く、`cheer_logs`にも一意制約（PK以外）が無い。同じ内容が2回届けば2行入る。`count`には応答（ack）も無いため、クライアントは「サーバーに届いたか」を知る手段が無い | 事実 |
| 5 | **スコア・順位確定・参照APIのいずれも`cheered_at`を使っていない**（`src/`全体で参照ゼロ）。遅れて届いたデータは「時間帯の絞り込みで漏れる」ことは無く、**`event_id`が合えば合計に全部入る**。`gauge=recent`の直近15秒もサーバーの`cheered_at`ではなく、画面側のポーリング受信時刻で計算するので、**まとめて届いた分は「その瞬間の急な勢い」として見える** | 事実 |
| 6 | 提案：発生時刻の追加は`cheer_logs`の列追加（マイグレーション）が要り変更量は中。重複防止は`count`に連番（`seq`）を付ける案が最小で、サーバー側は小さい。どちらも**ネイティブ側の仕様確認が先** | 推測 |

## 1. `cheered_at`に入る時刻の出どころ

### 1-1. クライアントが送る`count`のフィールド

【事実】`public/index.html:1097-1110`（`BATCH_SIZE = 5`、`:1037`）：

```js
send({
  type: 'count',
  id: deviceId,
  value: cheerBatchSum,              // 5回分の強度の合計
  duration_ms: Date.now() - cheerBatchStartedAt,   // 最初のサンプルから送信時までの経過ミリ秒
});
```

- **時刻（発生時刻・送信時刻）のフィールドは無い。連番・メッセージIDも無い。**
- `duration_ms`は「バッチの最初のサンプルを受け取ってからの経過時間」で、**時刻ではなく長さ**。通常は約5秒前後（1秒間隔で5回）
- BLEのペイロード（`spec.md` 5.1）には`num`フィールドがあるが（`payload = { num, accel, volt, rssi }`）、**`index.html`は`num`を一切読んでいない**（`payload.num`の参照ゼロ）。`num`の意味（デバイス側の連番かどうか）は【未確認】

### 1-2. サーバー側の扱い

【事実】
- `count`ハンドラ（`src/websocket/index.js:312-343`）が読むのは`msg.id`・`msg.value`・`msg.duration_ms`のみ。それ以外のフィールドは読まない（付いていても無視される）
- `insertCheerLog`（`src/db/cheerstickQueries.js:322-329`）のINSERT文は`device_id, user_id, event_id, target_id, intensity, duration_ms`の6列のみ。**`cheered_at`は指定しない**
- `cheer_logs.cheered_at`は`TIMESTAMPTZ NOT NULL DEFAULT NOW()`（`migrations/001_initial_schema.sql:166`）。**PostgreSQLがINSERTを実行した時刻**になる

【結論】`cheered_at`＝サーバー（DB）のINSERT実行時刻。クライアントの時計は一切反映されない。

### 1-3. 受信時刻とのずれ（再送と関係なく起きるもの）

【事実】`cheered_at`は「メッセージを受信した時刻」ではなく「INSERTを実行した時刻」。`pg.Pool`の待ち行列（最大5秒、`src/db/index.js:6-8`）が伸びていると、受信からINSERTまでの間に遅れが入る。
`cached`モード（現行の本番設定）では、デバイス情報・live試合の取得をキャッシュするため、この遅れは`legacy`より小さい。

【推測】将来、INSERTをまとめて書く（`large-event-8000-investigation.md` G-3のS2案等、1〜2秒ごとにflush）場合、`cheered_at`はflush時刻になり、最大で数秒ずれる。現状は`cheered_at`を使う集計が無いため影響は出ないが、使う集計を作るときは考慮が要る。

## 2. 遅れて届いた`count`の扱い

### 2-1. 試合が終わった後に届いた`count`

【事実】`event_id`は、受信（処理）時点で**そのデバイスが選択中のチームに`status='live'`かつ`hidden_at IS NULL`の試合があるか**で決まる（`findLiveEventForOrganization`、`cheerstickQueries.js:268-278`）。クライアントが「いつの`count`か」は判定に使われない。

| 受信時点の状況 | 結果 |
|---|---|
| そのチームにlive試合が無い（`finished`/`paused`/`scheduled`のみ） | **記録されない**（`if (liveEvent)`の外。`websocket/index.js:329-340`）。応答も無く、クライアントはエラーにも気付かない |
| `cached`モードで、終了操作の直後（最大2秒） | **旧`event_id`で記録されうる**（live試合キャッシュ、TTL 2秒。管理画面経由の終了は同一プロセス内では即時破棄される。`spec.md` 12.6章）。複数プロセスでは他プロセスが最大2秒遅れる（`cluster-mode-investigation.md` 1-3） |
| そのチームが**次の試合でliveになっている** | **次の試合の`event_id`で記録される。** 前の試合中に発生したデータでも、受信時刻で振り分けられる |
| 選択中のチームが変わった／デバイスの選択が未完了（`selected_organization_id`がNULL） | 現在の選択に従う。NULLなら記録されない（`:325`） |
| 推し（`current_target_id`）が未選択 | 記録される。`target_id`はNULL（イベント合計には入り、選手別には入らない。`large-event-8000-investigation.md` C-3） |

【推測】再接続の遅れが大きい（数分〜）ほど、「前の試合の応援が次の試合に混ざる」可能性が上がる。ただし、1台のデバイスが選べるチームは1つ（C-1）で、同じチームに連続する試合（同じ`organization_id`の別イベント）が組まれる場合に限られる。**対抗戦のペア（2イベント）が同時にliveで、かつ試合間の切り替えが無ければ起きない**。

### 2-2. 再接続の直後に同じ内容が二重に届く経路

【事実】WebView側の経路：
- **WebViewは再送しない。** `send()`はWebSocketが`OPEN`でなければ何もしない（`index.html:651-655`）。失敗した`count`を溜める配列・再試行は存在しない
- 再接続のたび、`connect`を送り直して応答を待つ。応答が`complete`なら**ウェルカム画面を表示し、応援中画面（`cheeringCard`）を隠す**（`renderConnect`→`hideAllCards`、`:657-661`・`:869-870`）
- `onCheerStickData`は応援中画面が隠れている間は即`return`する（`:1067`）。**STARTを押し直すまで何も処理しない**（`:932-934`）
- 組みかけのバッチ（`cheerBatchCount`・`cheerBatchSum`・`cheerBatchStartedAt`）は**再接続でリセットされない**。切断をまたいでバッチが完成した場合、`duration_ms`は切断時間を含む長い値になり得る（`Date.now() - cheerBatchStartedAt`）。ただし組みかけの最大4サンプル分のみで、量は小さい

【事実】サーバー側の経路：
- `count`は**ackを返さない**（`websocket/index.js:341`「レスポンス不要」）。クライアントは各`count`がサーバーに届いてINSERTされたかを知らない
- 重複排除は無い：`count`に冪等キーが無く、`cheer_logs`にPK（UUID自動生成）以外の一意制約が無い（`001:157-166`）。**同じ内容のメッセージが2回処理されれば2行入る**
- 1台のデバイスについて、新旧2本のWebSocketから同時に`count`が届く経路は、WebView側には無い（`cluster-mode-investigation.md` 1-2）。サーバー側で二重になる経路も見当たらない

【未確認（ネイティブ側の仕様）】依頼文の「ネイティブが保持して再送する」データが、**どの層・どの形式**かによって、影響が大きく変わる。

| 解釈 | 内容 | WebView・サーバーへの影響 |
|---|---|---|
| (a) **スティック↔アプリ間（BLE）**の保持 | BLEが途切れている間のセンサーデータを、アプリが保持し、BLE復帰後にまとめて`onCheerStickData`へ渡す | WebViewは**1件ずつ`onCheerStickData`が呼ばれた扱い**で5件ごとに`count`を作る。**短時間に連続で呼ばれると、5秒ぶんの応援が瞬間的に複数の`count`として送られる**（`duration_ms`は極端に短くなる）。応援画面が表示中でWebSocketがOPENなら、そのまま記録される。**過去の応援が受信時刻で記録される** |
| (b) **アプリ↔サーバー間（WebSocket）**の保持 | アプリがWebSocketのフレームを直接保持・再送する | `index.html`の`send()`を経由しない独自実装になる。本リポジトリのコードには**該当する処理が無い**。ネイティブ側がWebViewとは別にサーバーへ`count`を送っているなら、それは本調査の範囲外の経路で、**重複・二重カウントの危険がある**（WebView経由の`count`と、ネイティブの再送が両方届く） |
| (c) **WebView↔ネイティブ間（JSブリッジ）**の保持 | WebViewが読み込まれる前・非表示の間に、ネイティブが`onCheerStickData`の呼び出しを溜め、準備完了後に連続呼び出し | (a)と同じ形（連続呼び出し）。ただし**応援中画面が隠れていると全部捨てられる**（`:1067`） |

→ **ネイティブの再送が(a)(c)なら、「発生時刻のずれ」が主な影響で、重複は起きない。(b)なら重複が起きうる。** Vanstone様への確認項目（末尾）。

【推測】(a)(c)で、再接続の直後に**STARTが押されていない状態**（現行は再接続すると必ず完了画面に戻る）なら、溜まっていたデータは**全部捨てられ、記録されない**（過少カウント）。逆にSTARTを押し直した後に流れ込めば、過去のデータが「その時点の応援」として記録される。**どちらも「サーバーの記録が実際の応援と時間軸でずれる」方向の影響**で、後者のほうが総量は保たれる。

## 3. スコア集計・順位確定への影響

### 3-1. `cheered_at`を使う集計

【事実】`src/`・`public/`の全ファイルを`cheered_at`で検索：

| 場所 | 使用 |
|---|---|
| `migrations/001_initial_schema.sql:166, 173, 307-308` | カラム定義・コメント・インデックス`idx_cheer_logs_cheered_at` |
| `scripts/load-test/measure-latency.js` | 負荷試験のレイテンシ計測用（送信時刻との差を取る。本番機能ではない） |
| `scripts/cheer-log-write/local-verify.js:217` | ローカル確認の並び替えのみ |
| `public/battle.html:695` | コメントのみ（「`cheered_at`ではなくポーリング受信時刻を使う」） |
| **`src/`のSQL・コード** | **使用ゼロ** |

→ **スコア・順位・参照APIのいずれにも、時間帯の絞り込みや`cheered_at`による並び替えは無い。**
（`cheered_at`のインデックスは存在するが、現状どのクエリからも使われていない。9本のインデックスの1つとして、INSERTのたびに更新だけされている。`large-event-8000-investigation.md` A-3）

各集計の絞り込み条件（`cheerstickQueries.js`）：

| 集計 | 絞り込み | 時間条件 |
|---|---|---|
| 対抗戦スコア（`getEventIntensityTotal`、`:1224`） | `WHERE event_id = $1` | なし |
| 選手別（`getEventTargetScores`、`:755`／`getAllTimeTargetScores`、`:777`） | `WHERE cl.event_id = $1`（全期間は絞り込みなし） | なし |
| 順位確定（`computeUserRanking`、`:1251`／`computeTargetRanking`、`:1270`） | `WHERE cl.event_id = $1`、`GROUP BY`、上位20 | なし |
| 参照API（`getRecentEventCheerTotals`、`:231`／`getAllTimeCheerTotal`、`:251`） | `WHERE cl.device_id = $1 AND e.hidden_at IS NULL`、並びは`e.starts_at DESC`（**イベントの開始日時**） | なし（`cheered_at`ではなく`events.starts_at`で並べる） |

### 3-2. `gauge=recent`の直近15秒

【事実】`public/battle.html`の`gauge=recent`（`window`パラメータ既定15秒、`:333`）は、**サーバーの`cheered_at`を見ない**。
3秒（デモは1秒）ごとのポーリングで取得した**イベント合計値**を、**ポーリング受信時刻**とともに履歴に積み、窓の最古との差分で勢いを出す（`:695-720`、`:761-784`）。

【事実】したがって、遅れて届いた`count`が、まとめて記録されると：
- 合計値が**その時点で一気に増える**。ゲージは「その瞬間に大きな応援が来た」として反応する（ポーリング間の増加分として見える）
- 本来の発生時刻（過去）には**さかのぼって反映されない**（そもそも時刻の概念が無い）
- 後述（3-3）のとおり、時間帯で絞った集計が無いので、「別の時間帯に入る」ことでスコアがずれることは無い。**ずれるのは「ゲージの勢いの見え方」と「試合をまたぐ`event_id`の割り当て」のみ**

### 3-3. 遅れて届いたデータが集計から漏れる／別の時間帯に入る条件

| 条件 | 結果 | 区分 |
|---|---|---|
| 受信時にそのチームにlive試合が無い | **漏れる**（記録されない。2-1） | 事実 |
| 受信時に`cached`のキャッシュが「liveなし」を保持している（試合開始直後の最大2秒） | **漏れる**（`spec.md` 12.6章の既知の挙動） | 事実 |
| 受信時に同じチームの**別の試合**がliveになっている | **別の`event_id`に入る**（前の試合の応援が次の試合の得点になる） | 事実 |
| 選択チームの変更・推し未選択 | チーム変更後のチームの試合に入る。推し未選択なら選手別に入らない | 事実 |
| 上記以外（試合中に再接続して届いた） | **漏れない。`event_id`が合えば合計に全部入る**。ゲージ上は「受信時の急な増加」として見える | 事実 |
| 時間帯で絞る集計（例：「後半だけ」「最後の5分」） | **現状、そのような集計は存在しない** | 事実 |

【推測】将来「時間帯別の応援量（例：5分ごとの推移グラフ）」を作る場合は、`cheered_at`＝受信時刻になるため、再接続後のまとめ送りが**1つの時間帯に集中して見える**（実際は過去数十秒〜数分に分散していた応援が、再接続した瞬間に山になる）。**そのような集計を作る前に、発生時刻の扱いを決める必要がある**。

## 4. 提案（実装はしない）

### 4-1. 案T：発生時刻を`count`に付ける

**内容**：クライアントが`count`にバッチ最初のサンプル時刻を付ける。サーバーは、その時刻を`cheer_logs`に保存する。

| 項目 | 内容 |
|---|---|
| クライアント（`index.html`） | `send`に`occurred_at: cheerBatchStartedAt`（エポックミリ秒）を追加。ネイティブが保持・再送する場合は、保持データ側の**元の時刻**を使う必要がある（`Date.now()`はWebViewが呼ばれた時刻＝再送時刻になるので意味が無い）。**ネイティブが`onCheerStickData`のpayloadに時刻を付けて渡す仕様変更（Vanstone様側）が要る** |
| サーバー（`websocket/index.js`・`insertCheerLog`） | `msg.occurred_at`の検証（数値、未来の時刻・極端に古い時刻は丸める／拒否）、INSERTへ追加 |
| DB | **マイグレーションが必要。** 方法は2つ：①`cheered_at`をそのまま発生時刻にする（受信時刻が失われる。既存データとの意味が変わる）、②**新しい列**（例：`occurred_at TIMESTAMPTZ NULL`）を追加し、`cheered_at`は受信時刻のまま残す（推奨）。`cheer_logs`は数千万行規模になりうるため、`ALTER TABLE ... ADD COLUMN`はNULL許容・DEFAULTなしなら瞬時（PostgreSQL 11以降）。インデックス追加は重いので、使う集計ができるまで見送る |
| 集計への影響 | 現状、時間条件を使う集計が無いので**既存の集計は変わらない**。将来の時間帯集計から使える |
| 端末の時計の信頼性 | スマホの時計は狂いうる。**サーバーとの差を補正する仕組み**（接続時にサーバー時刻を返し、クライアントが差分を持つ）が無いと、発生時刻は信頼できない。`connect`応答に`server_time`を足すのが最小 |
| 変更量 | クライアント小、サーバー小、DB小（列追加）、**ネイティブ側（Vanstone様）の仕様変更・合意が最大のコスト**。互換性：古いクライアントは`occurred_at`を付けないので、NULLで受ける（受信時刻にフォールバック） |
| 古い`count`の扱い（試合が終わった後に届いた分） | 時刻が付けば「発生時刻が試合の`starts_at`〜`ends_at`の範囲内か」で`event_id`を決められる（現状は受信時のlive試合）。ただし、`status`が`finished`になった時刻を記録する仕組みは`events`の更新処理に見当たらず（`ends_at`の運用実態は【未確認】）、確実な終了時刻の記録が別途要る可能性がある。実装すると大きな変更になる |

### 4-2. 案D：サーバー側で重複を防ぐ

**前提**：重複が起きる経路が実在するか（2-2の(b)）を先に確認する。(a)(c)だけなら不要。

| 案 | 内容 | 影響範囲・変更量 |
|---|---|---|
| **D1：`count`に連番`seq`を付ける**（デバイス単位で単調増加） | クライアントは`seq`を付ける（ネイティブ再送なら、元のデータの連番）。サーバーはデバイスごとの最大`seq`を覚え、それ以下は破棄 | クライアント小。サーバーは`seq`の保持が要る。**プロセス内メモリ（`ws`ごと）では再接続で消える**ので、デバイス単位の永続（DBの列、または`devices`への`last_count_seq`）が要る。**DBへの書き込みが`count`ごとに増える**（1,600件/秒に対し`UPDATE devices`が増える）ため、8,000人規模では重い。プロセス内（再接続でリセット）で十分なケース（直近の重複だけ防ぐ）は軽い |
| **D2：`cheer_logs`に一意制約**（`device_id, seq`） | `INSERT ... ON CONFLICT DO NOTHING` | DB変更（列追加＋一意インデックス）。**9本のインデックスがさらに増えてINSERTが重くなる**（`large-event-8000-investigation.md` A-3）。重複を確実に防げる。行数が数千万規模で、一意インデックスの追加は時間がかかる |
| **D3：`count`にackを返し、クライアントが再送管理する**（at-least-once＋重複排除） | サーバーが`ack{seq}`を返し、クライアントは未ackを保持・再送 | 最も堅牢だが、**WebView・サーバー・ネイティブの全てに及ぶ大きな変更**。1,600件/秒の送信メッセージが2倍になる |
| **D4：何もしない（現状）** | 重複が起きる経路が無い（(a)(c)）、または重複量が許容できる | 変更ゼロ。**まず経路の実在を確認すべき** |
| **D5：サーバー側の時間窓での簡易重複判定** | 同じデバイスから、直前の`count`と同じ`value`・`duration_ms`が、短時間（例：数百ミリ秒）に届いたら破棄 | 小さい変更だが、**正当な連続した同じ値（`value`が同値のバッチ）を誤って落とす**。強度の合計値は離散的で同値が頻出するため、誤判定が多い。非推奨【推測】 |

### 4-3. 推奨の見立て

1. **まずVanstone様に再送の仕様（確認項目）を聞く。** 回答次第で、案T・案Dの要否が決まる（2-2の(a)(b)(c)）
2. 現状のサーバー・WebViewは、**重複排除が無いことを前提に「(a)(c)なら問題なし、(b)なら二重カウント」**という構造。(b)の可能性があれば、先にD1/D2/D3のいずれかを検討
3. **時間帯別の集計を新たに作らない限り、案Tは急がなくてよい**（現状の集計はすべて`event_id`単位で、時間条件が無い）。急ぐなら、`gauge=recent`の見え方（まとめ届きで勢いが跳ねる）への影響を、ネイティブ側の再送のタイミング（バースト幅）次第で実機確認する
4. 8,000人規模でのまとめ送りの影響：再接続が同時多発すると、再送データが**一斉に流れ込み、短時間に`count`が増える**。`large-event-8000-investigation.md` D-3の再接続の山に、**保持データのまとめ送り（1台あたり数件〜数十件）が上乗せ**される。ただし現行は再接続でSTART待ちになる（2-2）ため、(a)(c)なら流れ込みは起きにくい【推測】

## 確認依頼リスト

### Vanstone様（ネイティブ側）への確認事項

1. **「通信が確立できなかったデータを保持する」の対象**：①スティック↔アプリ（BLE）の間か、②アプリ↔サーバー（WebSocket）の間か、③アプリ→WebView（`onCheerStickData`呼び出し）か。複数あれば全て
2. 保持するデータの**形式**（`onCheerStickData`のpayloadそのものか、`count`メッセージか）と、**保持する期間・上限件数**（何分、何件まで）
3. 再送の**方法と速度**（`onCheerStickData`を1秒間隔のまま遅れて呼ぶのか、溜めた分を連続して一気に呼ぶのか）
4. 再送時に**発生時刻や連番を付けられるか**（`payload.num`の意味。`spec.md` 5.1の`num`がデバイス側の連番か）
5. アプリが**WebViewを経由せず、サーバーのWebSocketへ直接`count`を送る**実装はあるか
6. 再接続（WebViewのWebSocket再接続）のあと、**保持データをいつ流すか**（WebViewが応援画面に戻る前に流す設計か）

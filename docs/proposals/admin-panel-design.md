# CheerStick 管理画面 設計案（検討用ドラフト）

2026-07-25 作成　※実装はまだ行わない。方針確認のための資料

## 前提

- 利用者：当面KMT様お一人
- アクセス：既存のオフィスIP制限をそのまま流用
- 実装時期：優先度は低め（Vanstoneとの調整・8月リリースを優先）。
  本資料は方針を固め、着手できる状態にしておくためのもの

## 置き場所の提案

`admin.cheerstick.com` を使用する。

理由：
- ドメイン・SSL証明書は既に取得済み（`spec.md` に「未設定、優先度低」と記載のもの）
- `app.cheerstick.com`（一般ユーザー向け）とは完全に別ドメインになるため、
  IP制限をサブドメイン単位でかけられ、設定がシンプルになる
- 将来Grafana等を導入する場合も、パスを分けて共存できる

```nginx
server {
    server_name admin.cheerstick.com;
    allow 49.156.217.121;
    deny  all;

    location /api/ {
        proxy_pass http://127.0.0.1:3000;   # 既存アプリに相乗り
    }
    location / {
        root /var/www/cheerstick-admin;      # 管理画面の静的ファイル
    }
}
```

技術構成は `public/index.html` と同様、**フレームワークを使わない素のHTML/JS**を
想定。React等を新規導入すると学習・保守コストが増えるため、既存スタイルに揃える。

## 機能一覧と段階分け

ご要望いただいた5機能を、**バックエンドの準備状況**で3段階に分けた。

### フェーズA：既存の仕組みに画面を被せるだけ（実装コストが最も低い）

| 機能 | 現状 |
|---|---|
| **試合状態の切り替え** | APIは既にある（`PATCH /api/v1/admin/events/:id/status`）。画面から叩くだけ |
| **デバイス所有者リセット** | 今日作成したSQL手順がある（`runbook.md`）。画面から実行できるようAPI化するだけ |

いずれも裏側のロジックは完成済みで、**フォームとボタンを用意するだけ**の作業。
半日〜1日程度と見込む。

### フェーズB：今日整備したDB列を活用（比較的軽い）

| 機能 | 現状 |
|---|---|
| **チーム・選手のロゴ/プロフィール設定** | 今日 `logo_url` / `image_url` / `profile_text` の表示側を整備済み。管理画面からの**入力**フォームを作る |
| **チームカラーの設定** | `organizations.color` は既にある。同様に入力フォームを作る |

**画像のアップロード機能までは今回含めない**ことを提案する。現状、画像は
サーバー上に直接配置されている（`/var/www/cheerstick-app/images/...`）。
まずは「画像URLを入力する」形の簡易版とし、ファイルアップロード機能は
必要性が高まった時点で別途検討する。1〜2日程度と見込む。

### フェーズC：新規に作る必要がある（最も重い）

| 機能 | 内容 |
|---|---|
| **応援状況の可視化ダッシュボード** | 現在接続中のデバイス数、チーム別・試合別の応援量推移などを集計して表示する。集計クエリ・APIを新規に作る必要がある |

これは工数だけでなく、**「何を見たいか」の仕様検討自体が必要**。
例えば以下のような項目が考えられるが、優先順位はご相談したい。

- 現在オンラインのデバイス数（リアルタイム）
- 試合ごとの応援量推移（グラフ）
- チーム別の応援量比較
- 過去の試合との比較

2〜3日程度を見込むが、**見たい情報の絞り込み次第で変動する。**

## 進め方の提案

```
1. フェーズA（試合状態・所有者リセット）　→ 8月リリース前後、余裕があれば着手
2. フェーズB（プロフィール・チームカラー） → フェーズAの後
3. フェーズC（可視化ダッシュボード）      → リリース後、要件を詰めてから着手
```

**フェーズCは急がないことを提案する。**理由は2つ。

- 現状、`cheer_logs` に十分なデータが溜まっていない（本番稼働がこれから）ため、
  今ダッシュボードを作っても中身が空に近い
- 「何を見たいか」は、実際に試合が始まり運用してみないと固まりにくい

**フェーズA・Bは、Vanstoneとのやり取りが停滞している時間帯の
"手が空いた時" に進めるのに適している。**社外依存が無く、いつ着手しても良い。

## フェーズC 詳細設計（2026-07-25 追記）

### 想定する見る場

まず管理画面で検証し、将来的に会場の大型スクリーン等への表示も見据える。
**両対応を前提に、最初からAPIを設計する。**

### ニックネームの公開について

同意管理はサーバー側で持たず、アプリ側の表示・説明書でカバーする方針で確定。
そのためサーバーは「同意した人だけ表示」という制御ができない点に留意する
（登録した全員が等しく表示対象になる）。

**軽い提案：** 将来的に「表示させない」設定（オプトアウト）を用意すると
安心材料になる。今回のスコープには含めないが、`targets` または `users` に
`hide_from_leaderboard`（boolean, default false）のような列を1つ足すだけで
後から対応できるよう、設計上は余地を残しておく。

### データ構造（案）

「応援エントリ」を1行＝1デバイス（＝1人のユーザー）として、以下の列を
持つ集計ビューを想定する。

| 列 | 内容 |
|---|---|
| `rank` | 応援量による順位 |
| `nickname` | 登録時の名前 |
| `oshi_name` | 選んだ推し選手・マスコット名（`targets.name`） |
| `team_name` | 所属チーム名（`organizations.name`） |
| `team_color` | チームカラー（表示の色分け用） |
| `cheer_amount` | 応援量（`cheer_logs` の集計） |

**ソート・絞り込み軸：** 応援量順（デフォルト）、ニックネーム、選手別、チーム別。
チーム・選手・試合（イベント）でのフィルタリングも可能にする。

### API設計（案）

```
GET /api/v1/admin/leaderboard
  ?event_id=<試合ID>       任意。指定が無ければ全期間集計
  &team_id=<チームID>      任意
  &target_id=<選手ID>      任意
  &sort=cheer_amount|nickname|team|oshi   デフォルト: cheer_amount
  &order=desc|asc          デフォルト: desc
  &limit=&offset=          ページング用
```

このエンドポイントは `/api/v1/admin/` 配下に置き、既存のIP制限をそのまま適用する。
将来会場表示用に公開する場合は、**別のパス**（例：`/api/v1/public/leaderboard`）
を新設し、IP制限の外に出す。混在させない。

### 更新頻度

「ある程度でよい」とのことなので、**画面側で数秒〜十数秒おきにポーリングする**
方式で十分（WebSocketでのリアルタイム配信は今回不要。実装・運用コストに見合わない）。

### フロントエンドの構成（提案）

**まずAPIを作る。** これは管理画面でも会場表示でも共通して必要になるため、
どちらに転んでも無駄にならない。

フロント（画面）は、用途に応じて**2つに分ける**ことを提案する。

| 画面 | 用途 | 特徴 |
|---|---|---|
| **管理画面（検証用）** | KMT様が内容を確認・検証 | ソート・フィルタのUI付き。オフィスIP制限 |
| **会場表示用ページ** | 大型スクリーン・OBSへの投影 | 大きな文字、自動スクロール、操作不要。フィルタ無しの読み取り専用 |

会場表示は、**OBSの「ブラウザソース」機能でURLを指定するだけ**で映せる設計にする。
専用のツール連携は不要。既存の `public/index.html` と同じ素のHTML/JS/CSSで作成できる。

いずれもAPIを叩くだけの薄いページなので、**両方をClaude側で作成しても
工数は大きくない。** ただし会場表示は「大画面で見て恰好がつくデザイン」が
必要になるため、V・ファーレン長崎のブランドイメージ（チームカラー等）を
踏まえたデザイン確認を別途行うことを想定しておく。

### フェーズC 個人情報の扱いについて（確定事項）

- **ニックネーム表示の割り切り方が確定：** `name` フィールドは今後も
  1つのまま（表示用とニックネーム用を分けない）。代わりに、
  **登録画面に「ニックネームでご登録ください」という案内文を追加する。**
  この案内文の追加は、フェーズAの実装指示書に含める（画面変更のみ、
  データ構造の変更は無し）。
- **メールアドレスの収集は継続する。** 目的は「トラブル時の連絡手段」。
  Apple/Google双方のアプリストア審査で、メールアドレス収集について
  **申告することが確定済み。** この申告はVanstone様のアプリ申請作業に
  含まれるため、ブリッジ仕様のやり取りの中で申し送り事項として
  共有しておくこと（本設計案とは別件だが、同じタイミングで
  思い出せるよう記録する）。

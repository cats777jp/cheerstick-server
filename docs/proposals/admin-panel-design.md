# 管理画面 機能整理・実装方針（2026-07-27 改訂）

## 1. 前提条件（2026-07-27 確定）

- **利用者は KMT のみ。** 現時点で社外・観客への公開は想定しない。
- したがって **会場スクリーン表示用の画面は今回のスコープ外**。
  7/25版で未回答だった「管理画面用／会場表示用の2画面構成でよいか」は、
  **当面1画面で足りる** という結論とする。
- ニックネーム公開に伴う同意設計の論点は、会場表示を行わないため
  当面発生しない（将来スコープに入った時点で再検討）。
- **フェーズA・B・C すべてを進める方針。** ただし段階的に実施する。
- **500台実機負荷試験は、実施の予定はあるが時期未定。**
  会場確保・参加人員の手配が必要なため、日程を前提にした計画は立てられない。
  → **ダミーデータによる検証を先行させる。**
- **チーム・選手のプロフィール／カラー設定は優先度A。**
  これらのデータが無いと、ユーザーがチーム選択・推し選手選択を行えない。
- **表示コンテンツを当面リーグワン（三菱重工相模原ダイナボアーズ）へ切り替える。**
  V・ファーレン長崎様のロゴ・チーム名の使用許諾が未取得と判明したため（8章参照）。
  Jリーグ側のデータは削除せず保持し、許諾取得後にV・ファーレン長崎表示へ切り替える。

## 2. アクセス制限（確定）

**IP制限 ＋ 簡易パスワード** とする。実現方式は **nginx の Basic 認証**。

```nginx
server {
    server_name admin.cheerstick.com;

    # 既存の管理API と同じ考え方（2026-07-25 に実装済みのものと同一IP）
    allow 49.156.217.121;
    deny all;

    auth_basic           "CheerStick Admin";
    auth_basic_user_file /etc/nginx/.htpasswd;

    # 管理画面の静的ファイル
    location / {
        root /var/www/cheerstick-admin;
    }

    # ★重要：API を同一オリジンに寄せる
    location /api/ {
        proxy_pass http://127.0.0.1:3000;
    }
}
```

### 方式選定の理由

- **認証コードを自作しない。** ログイン画面・セッション管理・トークン検証を
  実装すると、そこが新たなバグと脆弱性の発生源になる。
  リリース直前に増やすべきリスクではない。
- **API を同一オリジンに寄せる。** 管理画面を `admin.cheerstick.com`、
  API を `api.cheerstick.com` と別オリジンにすると、CORS と認証情報
  （credentials）の受け渡しが必要になる。同一オリジンなら、ブラウザが
  Basic 認証のヘッダを自動付与するため、追加実装が不要。
- `.htpasswd` は git 管理下に置かないこと。`runbook.md` に
  「どこに置いたか」と「再発行手順」のみ記録する。

### 会場での運用について（IP制限で問題ない理由）

試合の開始・一時停止（ハーフタイム）・終了は**運用者が会場で手動操作する。**
ロスタイムの発生など、自動化が困難な要素があるため当面この運用とする。

一見するとオフィスIP限定では会場から操作できないように思えるが、
**KMT様のVPNはオフィスのVPNサーバー経由でインターネットに出る構成**のため、
外部から接続しても送信元IPは `49.156.217.121` のまま見える
（2026-07-25 に確認済み）。したがって**会場からVPN接続すれば
IP制限をそのまま通過できる。**

**運用上の注意：** 会場での操作はVPN接続が前提となる。試合中にVPNが
切断されると状態操作ができなくなるため、**事前に会場から疎通確認を
行っておくこと。**

### 管理画面 #2（試合状態の切り替え）への設計上の要求

会場で手動操作する以上、**#2はスマートフォンからの操作を前提に作る。**

- ボタンを大きく、誤操作しにくい配置にする
- ロスタイム等に即応できるよう、画面を開いてから操作までの手数を最小にする
- 「終了」など取り返しのつかない操作は確認を挟む

後から直すより、最初から織り込むこと。

### 実装前に確認が必要な事項

`admin.cheerstick.com` について、過去の記録に食い違いがある。

- 「Route53レコード未設定、Grafana等用、優先度低」という記述
- 「証明書だけ取得済みの未使用ドメイン」という記述

**どちらが現状か、Claude Code で実地確認してから着手すること。**
DNS レコードと SSL 証明書の有無で、初日の作業量が変わる。

## 3. 機能一覧（優先度順・第2版で改訂）

| # | 機能 | 優先度 | 状況・根拠 |
|---|---|---|---|
| 0 | 管理画面の土台（ドメイン疎通・nginx・認証・共通レイアウト） | **A** | これが無いと他が載らない |
| 1 | 試合の登録・編集 | **A** | **登録手段が存在しない（現状は手動SQL）**。無いと毎試合の運用が回らない |
| 2 | 試合状態の切り替え | **A** | API実装済み（`PATCH /api/v1/admin/events/:id/status`）。#1と同一画面に同居 |

| 10 | チームカラー設定 | **A** | `organizations.color`。同上の理由でAへ引き上げ |
| 4 | 登録ユーザーの検索・確認 | A | 問い合わせ対応時に必須。#5と同一画面 |
| 5 | デバイス所有者のリセット | A | SQL手順は `runbook.md` にあり、API化のみ |
| — | **ダミーデータ生成スクリプト** | B | **第2版で新規追加。** 下記「フェーズCの進め方」参照 |
| 6 | 接続中デバイス数の確認 | B | WebSocketサーバーが既に接続を保持。**C の中で最も安い** |
| 7 | 応援可視化API（集計・ソート・絞り込み） | B | 順位／応援量／ニックネーム／選手／チーム |
| 8 | 応援可視化ダッシュボード画面 | C | 会場表示不要のため1画面でよい |
| 3 | デバイス(MAC)の一括登録（CSV） | C | **負荷試験の時期が未定のため優先度を下げた。** 日程確定時に前倒しすること |

### #9・#10 に関する重要な切り分け

チーム選択・推し選手選択の**画面と仕組みは既に実装済みで動作している。**
止まっているのは**中身のデータ**であり、選手は現在も
「サンプル選手A/B/C」のプレースホルダーのままである。

したがって、

- リリースを妨げているのは **管理画面の不在ではなく、実データの不在**
- **管理画面の完成を待たずに、SQLで先行してデータ投入を開始できる**
- 管理画面の役割は「その後の修正・追加を容易にすること」

背番号変更・移籍・写真差し替えは継続的に発生するため、そのたびに
SQLを叩く運用は現実的でない。よって優先度Aへの引き上げは妥当。

### #9 の権利関係（2026-07-27 状況確認済み）

**V・ファーレン長崎様の選手写真は、現時点で使用許諾を得られていない。**

ただし **これはリリースの必須条件ではない。** 2026-07-21 の実装時に
「選手写真が無い場合は頭文字アバターを自動生成して表示する」
フォールバックが入っており、写真ゼロでも選手選択画面は成立する。

許諾の要否は以下の3つに分かれる。

| 対象 | 許諾の要否 | 状況 |
|---|---|---|
| 選手写真 | 必要（肖像権） | **未取得。当面は頭文字アバターで代替** |
| 選手名・背番号・ポジション | 事実情報のため通常は問題になりにくい | 投入可能 |
| チームロゴ・チーム名 | 商標のため要確認 | **未確認。要フォロー** |

**リリースに向けて必要なのは選手名と背番号。** 写真は後から差し替え可能で、
その差し替えを容易にすることが #9 の目的そのものである。

なお、旧サーバー `http://157.120.32.31/html/img_menbers/{team_id}/{member_id}.jpg`
が404である件（2026-07-21 起票）は、許諾未取得である以上、
**所在調査を急ぐ必要は無くなった。** 許諾が得られた時点で改めて扱う。

### テストデータについて（2026-07-27 決定）

**ラグビーリーグワン・ダイナボアーズのデータをテストに使用する可能性がある。**
同チームからは利用許可を取得済み。

**副次的な利点：** ラグビーリーグワンはJリーグとは別カテゴリーであるため、
2026-07-22 に実装した**カテゴリー機能を初めて実データで検証できる**
（`CATEGORY_MISMATCH` の動作、カテゴリーによるチーム絞り込み）。
これまで単一カテゴリーでしか動作させていないため、
将来のマルチスポーツ展開に向けて一度通しておく価値がある。

**⚠ 必須条件：テストデータを本番データと混在させないこと。**
2026-07-22 に検証データのクリーンアップが発生している。同じ事故を
繰り返さないため、投入時点で分離しておく。カテゴリーと組織を分けておけば、
`category_id` 単位で一括削除できる。
**投入手順と削除手順をセットで `runbook.md` に記録すること。**

### 画面構成

7/25版では機能ごとに画面を想定していたが、**3画面に集約する。**

```
/            … ダッシュボード（#6 接続数、#8 応援可視化）
/events      … 試合管理（#1 登録・編集、#2 状態切替）
/teams       … チーム・選手設定（#9 プロフィール、#10 カラー）★優先度A
/devices     … デバイス・ユーザー管理（#4 検索、#5 所有者リセット、#3 CSV一括登録）
```

**#4・#5 を同一画面に寄せたのが整理の要点。**
「デバイス一覧」1画面に検索・所有者確認・リセットをまとめることで、
機能ごとに画面を作らずに済む。#3（CSV）も後日この画面に追加する。

**#9 は選手が30名規模のため、CSV一括ではなくフォームでの個別編集とする。**
写真URLの差し替えなど、1件ずつの修正が主になるため。

## 4. フェーズCの進め方（第2版で全面改訂）

### 前提の変更

第1版では「500台負荷試験で生成されるデータを使ってAPIを検証する」と
記載したが、**負荷試験の時期が未定であるため、この順序は成立しない。**

### ダミーデータ生成スクリプトを先行させる

`cheer_logs` に架空の応援データを流し込む単純なスクリプトを作成する。

**得られる効果**

- ダッシュボード（#7・#8）を実データ相当の状態で開発・検証できる
- **将来、負荷試験の日程が決まった際の予行演習にそのまま転用できる**
- 集計クエリの性能問題（インデックス不足等）を本番前に発見できる

**想定する規模**

- デバイス数：500件相当（負荷試験の想定規模に合わせる）
- 応援ログ：1試合分（90分×複数デバイス）
- チーム・選手：既存のサンプルデータを利用

半日程度で作成可能。**フェーズC全体の前提となるため、#6・#7 の直前に置く。**

### 改訂後の順序

```
ダミーデータ生成スクリプト → #6 接続数 → #7 API（ダミーデータで検証）
→ #8 画面 →（日程確定後）負荷試験でスクリプトを転用
```

## 5. 実装順序と工数見込み（第2版）

| 時期 | 範囲 | 見込み |
|---|---|---|
| **リリース前（〜8月第1週）** | #0 → #1・#2 → **#9・#10** → #4・#5 | 3〜3.5日 |
| **並行（社外依存）** | 選手写真の所在確認・使用許諾の取得 | — |
| リリース後 | ダミーデータ生成 → #6・#7 → #8 | 3日 |
| 時期未定 | #3 MAC一括登録（負荷試験の日程確定時に前倒し） | 1日 |

### 線引きの理由

- **#0〜#2、#9・#10 はリリースに直結する。** 特に #9・#10 が未設定だと
  ユーザーがチーム・推し選手を選べず、サービスとして成立しない。
- **#4・#5 は安価で運用価値が高い。** 「応援が反映されない」という
  問い合わせへの一次対応手段になる。
- **#3 は時期未定の負荷試験に紐づくため、後ろに置いてよい。**
  ただし日程が決まった時点で、直ちに前倒しすること。
- リリースまでの期間には **Vanstone様との往復** も入るため、
  リリース前の範囲は上記に絞ることを推奨する。

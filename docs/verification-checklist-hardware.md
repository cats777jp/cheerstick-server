## 1. 根本問題：応援動作→cheer_logsへの書き込みの実証（最優先・前提条件）

### 背景

本番DB（`cheerstick_production`）の`cheer_logs`は、2026-08-10時点の確認から
2026-09-11の再確認まで一貫して**0件のまま**であり、9/6のB-1/B-2実機検証を
挟んでも変化していない（`docs/spec.md` 11.7章・`docs/worklog.md`2026-09-11
エントリ参照）。4.3章のロジック上、書き込みには「デバイスの選択中チームに
`status='live'`の試合が存在すること」が条件であり、過去の実機検証でこの条件が
満たされていなかった可能性が高い。**今回の実機検証で、この条件を確実に満たした
状態で応援動作を行い、実際に`cheer_logs`へ行が入ることを初めて実証する。**

### 事前準備

- [ ] SSHで本番DB（`cheerstick_production`）に読み取り専用で接続できることを確認
      （`ssh -i C:\AWS\cheerstick-key\cheerstick-key.pem ubuntu@52.196.49.126`。
      runbook.md参照。前回・前々回セッションはこのSSH自体が権限クラシファイアに
      ブロックされ続けていたため、まずここが通るか確認すること）
- [ ] 管理画面（`https://admin.cheerstick.com`、KMT様オフィス固定IPからのみアクセス可）
      で新規テスト用イベントを1件作成する（例：「【実機検証】応援動作確認 20260XXX」）。
      対象organizationは実機のカテゴリー・チームと一致するものを選ぶこと
- [ ] 検証対象デバイスのMACアドレスを控える（実機のBLEスティック本体に記載、
      または検証機であれば`docs/runbook.md`「デモ用デバイスの登録」参照）

### 確認手順

1. 作成したテストイベントを管理画面の「開始」ボタンで`live`にする
   （8.0章の状態遷移表どおり、`scheduled`→`live`は確認ダイアログ無しで即座に遷移する）
2. 本番DBで対象イベントが実際に`live`になっていることをSELECTで確認
   ```sql
   SELECT id, title, status, organization_id FROM events WHERE id = '<作成したevent_id>';
   ```
3. Androidアプリ＋実機BLEスティックでペアリングし、WebView（`app.cheerstick.com`）で
   チーム選択（`select_team`）を行う。選択したチームが手順1で`live`にしたイベントの
   `organization_id`と一致していることを確認する
   ```sql
   SELECT mac_address, selected_organization_id, current_target_id
     FROM devices WHERE mac_address = '<検証デバイスのMACアドレス>';
   -- selected_organization_id が手順1のevents.organization_idと一致するか確認
   ```
4. 実際にスティックを振って応援動作を行う（数秒〜数十秒、複数回）
5. 応援動作の直後〜数分以内に、本番DBで`cheer_logs`へ行が入っているかSELECTで確認
   ```sql
   SELECT id, device_id, event_id, intensity, duration_ms, cheered_at
     FROM cheer_logs
     WHERE event_id = '<作成したevent_id>'
     ORDER BY cheered_at DESC
     LIMIT 20;
   ```
6. 検証後、テストイベントは管理画面の「終了」ボタン（確認ダイアログあり）で
   `finished`にし、`docs/runbook.md`の非表示化方針に従い放置せず後片付けする
   （物理DELETEは実装されていないため、`finished`のまま残ることは想定内。
   11.3章参照）

### 合格基準

- 手順3で、デバイスの`selected_organization_id`がテストイベントの`organization_id`と
  一致していることを確認できる
- 手順5で、`cheer_logs`に**応援動作の回数・タイミングにおおむね対応する行数**が
  `event_id = <作成したevent_id>`で記録されていることを確認できる
  （1回の応援動作＝1行とは限らない。クライアント側のバッチ送信仕様は`public/index.html`
  の`BATCH_SIZE`定数等に依存するため、行数の厳密な一致までは求めない）
- `intensity`・`duration_ms`が0や異常値（負値等）ではなく、応援の強弱に対応した
  妥当な値になっていることを目視確認する

### NGだった場合の切り分け方法

`cheer_logs`に行が入らなかった場合、以下の順に切り分ける。

1. **イベントが本当に`live`になっているか再確認**
   ```sql
   SELECT status FROM events WHERE id = '<作成したevent_id>';
   ```
   `live`以外（`scheduled`に戻っている、`paused`になっている等）であれば、
   4.3章の判定ロジック上DB保存はスキップされる仕様どおりの動作であり、バグではない。
   管理画面の操作ミス、または別セッションから誤って状態変更された可能性を疑う

2. **デバイスの接続先チーム（`selected_organization_id`）が意図した試合の
   `organization_id`と一致しているか再確認**（手順3のSQLを再実行）。
   一致していない場合、WebViewでのチーム選択操作自体をやり直す

3. **同一organizationで複数のイベントが同時に`live`になっていないか確認**
   （11.2章のTOCTOU既知課題。`findLiveEventForOrganization`は`LIMIT 1`のため、
   意図しない別イベント側に書き込まれている可能性がある）
   ```sql
   SELECT id, title, status FROM events
     WHERE organization_id = '<対象organization_id>' AND status = 'live';
   -- 2件以上liveがヒットする場合、cheer_logsが別のevent_idに記録されている可能性がある
   SELECT event_id, COUNT(*) FROM cheer_logs
     WHERE event_id IN (
       SELECT id FROM events WHERE organization_id = '<対象organization_id>'
     )
     GROUP BY event_id;
   ```

4. **pm2ログでWebSocket接続自体が成功しているか確認**（6.2章の接続ログ形式）
   ```bash
   pm2 logs cheerstick-server --lines 200 | grep -i '<検証デバイスのMACアドレス>'
   ```
   - 接続ログが無い、または`status:"error"`（理由コード`NO_ROW`/`NO_CATEGORY`/
     `EXCEPTION`）の場合：デバイスの`category_id`が未設定、またはWebSocket接続自体が
     確立していない。`docs/spec.md` 6.2章の判定ロジックに従い、`devices.category_id`を
     確認する
     ```sql
     SELECT mac_address, category_id FROM devices WHERE mac_address = '<MACアドレス>';
     ```
   - **注意：`connect`時の接続ログは存在するが、`count`メッセージ受信時・
     `cheer_logs` INSERT時のログは現行コード（`src/websocket/index.js`の
     `case 'count':`）に一切存在しない。** そのため「`count`メッセージ自体が
     サーバーへ届いているか」はpm2ログからは判別できない。この切り分けが
     必要な場合は、上記1〜3のDB確認で原因が絞り込めないときに限り、KMT様と
     相談のうえ一時的なデバッグログ追加（コード変更）を別途検討する
     （本チェックリストの範囲外）

5. **Androidアプリ側でWebSocket自体が`count`メッセージを送信できているか**
   （ネイティブアプリ側のログ・Android実機のUSBデバッグ等で確認。アプリ側の
   実装・ログ出力状況はVanstone/サーリューション経由の確認が必要になる場合がある）

## 3. 電池残量警告ロジック（2026-09-06対応、`public/index.html:1027-1028`付近）

**デプロイ状況：本番に反映済み（0.1節で確認済み）。追加のデプロイ作業なしで
そのまま検証可能。**

対象コード：`BATTERY_LOW_THRESHOLD = 3.0`（V）・`BATTERY_LOW_DURATION_MS = 60 * 1000`
（`public/index.html` 1027〜1028行目付近）。「3V以下の状態が60秒間連続した場合のみ
警告表示、途中で1回でも閾値を超えたら判定用タイマーをリセット」という仕様
（`docs/spec.md` 9.2章）が、実機の電圧降下パターン（実機依存でシミュレータとは
異なる可能性がある）に対して意図通り動くかを確認する。

### 事前準備

- [ ] 電池残量が少ない状態（3V付近）の実機、または電池を意図的に消耗させた実機を用意する
      （用意できない場合は、後述「NGだった場合の切り分け方法」の代替手段を参照）
- [ ] 応援中画面（`cheeringCard`）を表示できる状態（`START`操作済み）にしておく

### 確認手順

1. **瞬間的な電圧降下で誤発報しないことの確認**：LED点灯を伴う通常の応援動作を
   行い、電圧計測値が瞬間的に3V以下へ落ちても（Vanstone様指摘の事象）、
   「電池残少」表示（`#batteryDisplay`）が即座には出ないことを確認する
2. **60秒継続時の表示確認**：電池残量が実際に少ない状態（または意図的に消耗させた
   実機）で応援を継続し、3V以下の状態が60秒以上続いた時点で「電池残少」表示が
   出ることを確認する（ストップウォッチ等で概ね60秒であることを確認。厳密な
   秒数一致までは求めない）
3. **途中リセットの確認**：60秒に到達する前に、電池を一時的に交換する・充電済み
   スティックに差し替える等で電圧を回復させ、その後再び3V以下になった場合、
   タイマーが最初からやり直しになる（前回の経過時間が持ち越されない）ことを確認する
4. **セッションまたぎのリセット確認**：応援中画面を一度終了し（`START`を再度押す）、
   新しいセッションで警告表示状態・タイマーが持ち越されていないことを確認する

### 合格基準

- 手順1で、瞬間的な電圧降下では「電池残少」が表示されないこと
- 手順2で、60秒程度の連続した低電圧状態で確実に表示されること
- 手順3・4で、リセット条件どおりにタイマーがリセットされること

### NGだった場合の切り分け方法

1. ブラウザ（WebView）の開発者ツールが使える環境であれば、`console.log`で
   `payload.volt`の実測値を一定間隔で出力し、実機からの電圧値が想定通り
   3V付近で推移しているかをまず確認する（電圧値自体がノイズだらけ、または
   常に3V以上/以下に張り付いている等、閾値判定以前の実機側の問題を切り分ける）
2. `window.onCheerStickData`の**呼び出し間隔が1秒間隔という前提（5.1章）が
   実機で成立しているか**を確認する。9.2章の設計はタイムスタンプベース
   （`Date.now()`差分）のため呼び出し間隔のズレ自体は許容されるはずだが、
   極端に呼び出しが間引かれている（例：数秒に1回しか呼ばれない）場合は
   判定精度に影響する可能性がある
3. 実機が用意できず意図的な電圧降下を再現できない場合の代替手段：ブラウザの
   開発者ツールで`window.onCheerStickData({volt: 2.9, accel: {...}, rssi: -50, num: 1})`
   等を手動で直接呼び出し、ロジック単体の動作（サーバー側APIやDBには一切
   影響しない、クライアントJSのみの検証）を確認する

## 4. 通算応援量の表示（Vanstone様指摘②：`/api/v1/webview/reference`）

**デプロイ状況：本番に反映済み（0.1節で確認済み）。追加のデプロイ作業なしで
そのまま検証可能。**

**URLパスの修正要否について（確認済みの事実）**：`docs/spec.md` 3.3章に記載の
`GET /webviewrefer/?id=<MACアドレス>`は、史的経緯（初期仕様書PDF由来）の
**ドキュメント上の誤記であり、現行実装のエンドポイントは一貫して
`GET /api/v1/webview/reference?id=<MACアドレス>`である。** 今回のドキュメント
調査で、サーバー側実装（`src/routes/webview.js`・`src/app.js`）と、実際に
リクエストを送るクライアント側（`public/reference.html`の`fetch`呼び出し）の
**両方が既に正しいパス（`/api/v1/webview/reference`）を使用していることを
コード上確認済み。** そのためサーバー側・`public/`側のコード修正は不要
（`docs/spec.md`側の記載訂正のみが残っているが、今回はドキュメント更新は
対象外とのKMT様指示のため未実施）。

**ただし、Vanstone様の実機アプリ側が独自に`spec.md`の古い記載
（`/webviewrefer/?id=`）を参照して実装している可能性はコード調査だけでは
排除できない。** 実機検証では、この可能性を確認手順3で明示的に確認すること。

### 事前準備

- [ ] 通算応援量が既に蓄積されているテストデバイス・イベントを用意する
      （2026-09-11時点で本番`cheer_logs`は0件のため、項目1の手順で応援データを
      作ってから本項目を検証するのが望ましい。0件のままでも「0件と正しく表示される」
      ことの確認はできるが、実際の加算確認にはならない）

### 確認手順

1. Androidアプリで「過去成績参照」（BLE未接続時の画面、3.3章）を開く
2. 通算応援量（`all_time_intensity_total`）・直近3試合の内訳（`recent_events`）が
   表示されることを確認する
3. **実機アプリが実際にどのURLへリクエストしているかを確認する**
   （Android実機のプロキシツール・ネットワークログ、またはVanstone/サーリューション
   への確認依頼のいずれか）。`/api/v1/webview/reference?id=...`であれば正しい経路。
   もし`/webviewrefer/?id=...`等の存在しないパスへリクエストしていた場合、
   サーバー側は404を返すため、Vanstone側の実装がspec.mdの古い記載を参照して
   実装された可能性が高いと判断できる
4. DBの`cheer_logs`合計値と、アプリ表示の通算応援量が一致するか照合する
   ```sql
   SELECT COALESCE(SUM(intensity), 0) AS total FROM cheer_logs
     WHERE device_id = (SELECT id FROM devices WHERE mac_address = '<MACアドレス>');
   ```

### 合格基準

- 手順2で、エラー表示や無限ローディングにならず、数値が表示されること
- 手順4で、DB側のSUMとアプリ表示値が一致すること
- 手順3で、実際にリクエストされているURLが`/api/v1/webview/reference`であることを
  確認できること（＝表示不具合の原因がURLパス起因ではないと確定できる、
  または逆に原因がそこにあると確定できる）

### NGだった場合の切り分け方法

1. 手順3で存在しないパスへのリクエストが確認できた場合：**原因確定。**
   サーバー側の修正は不要（既に正しい実装のため）。Vanstone/サーリューション側へ
   正しいエンドポイント（`/api/v1/webview/reference?id=<MACアドレス>`）を
   あらためて提示し、アプリ側の実装修正を依頼する
2. 正しいパスへリクエストしているのに表示がおかしい場合：
   - レスポンスのHTTPステータス・JSON内容をNetworkログで直接確認する
     （`DEVICE_NOT_FOUND`＝MACアドレスがdevicesテーブルに存在しない、
     `MISSING_ID`＝クエリパラメータの`id`が渡っていない等、
     `src/controllers/referenceController.js`のエラー分岐を参照）
   - `ENABLE_REFERENCE_TOKEN`の本番設定値を確認する（現在`false`のはずだが、
     もし`true`になっている場合はMAC直指定ではなく`token`クエリが必要になり、
     アプリ側の実装と不整合が起きる）
     ```bash
     ssh -i C:\AWS\cheerstick-key\cheerstick-key.pem ubuntu@52.196.49.126 \
       "grep ENABLE_REFERENCE_TOKEN /home/ubuntu/cheerstick-server-new/.env"
     ```

## 5. 一括開始/停止/終了ボタンの実機接続時の操作感

**前提条件：0.1節のデプロイが完了していること**（対抗戦機能一式のデプロイに
一括操作UIも含まれる。項目2と同じデプロイ物）。項目1の合格は必須ではないが、
実機がlive中の試合に接続している状態を作る手順として項目1の手順1〜4がそのまま使える。

**ローカル確認済みの事項（今回あらためて確認不要）**：一括開始/停止/終了の
状態遷移ルール（`live`の行のみ一括「停止」対象にする等）は、pg-memによる
ローカル環境・claude-in-chromeでのブラウザ確認で2026-09-11・2026-09-14に
検証済み（`docs/spec.md` 9.3章、`docs/worklog.md`該当日エントリ参照）。
**今回の実機検証で確認したいのは、ロジックの正しさではなく、実機が接続中の
試合に対して一括操作を行った際の見え方・タイミングという運用面の観点。**

### 事前準備

- [ ] 実機（複数台が望ましい。難しければ1台を使い回してよい）を、それぞれ別の
      テストイベントの対象チームに接続させ、応援動作を行わせておく（項目1の手順を流用）
- [ ] 管理画面の試合一覧に、`live`中の試合を複数行表示させた状態にする

### 確認手順

1. 実機が応援動作を送信し続けている状態で、管理画面の一括「停止」ボタンを押す
   （対象行のチェックボックスを複数選択した状態で実行）
2. 停止操作の直後、実機側のWebView表示（応援中画面）に何らかの変化が起きるか、
   何も起きないか（サーバー側は`paused`遷移のみで、クライアントへのプッシュ通知は
   無い設計のため、通常は実機側の表示は変化しないはずである点に注意。4.3章参照）を確認する
3. 停止操作の直後に実機で応援動作を続けた場合、`count`メッセージ自体は
   引き続き送信されるが、`cheer_logs`への書き込みはスキップされる
   （8.0章の仕様どおり）ことをDBで確認する
   ```sql
   SELECT MAX(cheered_at) FROM cheer_logs WHERE event_id = '<停止したevent_id>';
   -- 停止操作の時刻より後のcheered_atが記録されていないことを確認
   ```
4. 複数行を選択して一括操作した際、管理画面の一覧表示・チェック状態の更新が
   実際の操作対象数に対してどの程度の速さで反映されるか（体感のタイミング）を確認する
   （9.3章の「1件ずつ順番に呼び出す」実装のため、対象件数が多いと反映に
   時間がかかる可能性がある。何件程度から体感できる遅延が出るかも記録しておく）
5. 一括「終了」（確認ダイアログあり）を、実機が接続中の試合に対して実行し、
   確認ダイアログの文言・選択件数の表示が意図通りであることを確認する

### 合格基準

- 手順2で、サーバー側の状態変更が実機側WebViewの表示に不整合を起こさないこと
  （エラー表示や画面フリーズ等が起きないこと）
- 手順3で、`paused`後の応援動作が`cheer_logs`に記録されないことを確認できる
  （8.0章の仕様どおりの動作であることの実機での再確認）
- 手順4で、明らかに使用に支障が出るような遅延（数十秒以上等）が発生しないこと

### NGだった場合の切り分け方法

1. 実機側WebViewにエラーが出た場合：ブラウザ開発者ツールのコンソールログを確認する
   （`read_console_messages`相当の確認。9.3章の設計は「サーバー側からのプッシュは
   無い」前提のため、そもそも実機側が停止をリアルタイムに検知する仕組みは
   存在しない。もし実機側で何らかのエラーが出た場合はサーバー側の一括操作とは
   無関係な、別要因の可能性が高い）
2. 手順3でDBに想定外の行が記録されていた場合：11.2章のTOCTOU既知課題（同一
   organizationで複数`live`が同時に存在しうる）を疑い、項目1の切り分け手順3と
   同じ手順で確認する
3. 反映が極端に遅い場合：`pm2 logs cheerstick-server`で個別の`PATCH .../status`
   リクエストのレスポンスタイムに異常が無いか確認する（8.2章の状態変更ログで
   各行の処理時刻を追える）

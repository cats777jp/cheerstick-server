# 引継ぎドキュメント更新手順

このセッションで行った作業を `docs/` に反映する。**手順を飛ばさないこと。**

## 手順

### 1. 今回の変更内容を把握する

```bash
git status
git diff --stat
git log --oneline -5
```

### 2. `docs/worklog.md` に追記する（追記のみ・過去エントリは触らない）

ファイル先頭の最新エントリの上に、以下の形式で追加する。

```markdown
## YYYY-MM-DD セッション

### 実施したこと
- （箇条書き。何を、なぜ、どうしたか）

### 変更したファイル
- （主要なもののみ）

### 判明した事実 / 想定と違ったこと
- （なければ「特になし」）

### 次回への申し送り
- （未完のもの、確認が必要なもの）

### 未解決のまま残した課題
- （あえて手を付けなかったものと、その理由）
```

### 3. `docs/spec.md` を更新する

仕様に関わる変更（API追加・DB変更・画面追加・挙動変更）があった場合のみ。

- **既存の記述を消さない。** 追記するか、該当箇所を更新して末尾の「変更履歴」に
  「いつ・何を・なぜ変えたか」を1行追加する
- マイグレーションを追加した場合は「マイグレーション適用状況」も更新する
- 今回触れていない機能セクションは、必ずそのまま残す

### 4. `docs/runbook.md` を更新する

環境・接続情報・手順に変更があった場合のみ（IP、ドメイン、プロセス構成、デプロイ手順など）。

### 5. 削除行のチェック（必須）

```bash
git diff --stat docs/
git diff docs/
```

**削除行が1行でもある場合は、ここで止まる。**
何をなぜ消したかをユーザーに説明し、意図的な削除であることの確認を取ってから次へ進む。
過去に、引継ぎ書から実装済み機能の記述が意図せず消える事故が起きている。

### 6. ドキュメントのみを単独でコミットする

```bash
git add docs/
git commit -m "docs: <今回の作業を一行で>"
```

コード変更と同じコミットに混ぜないこと。後から差分を追えなくなる。

### 7. ユーザーへ報告する

以下を簡潔に伝える。

- 今回docsに書いた内容の要約（3行以内）
- `git diff --stat docs/` の結果（追加/削除行数）
- 次回セッションの冒頭で着手すべきこと
- コミットハッシュ
